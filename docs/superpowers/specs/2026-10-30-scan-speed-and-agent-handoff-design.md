# 扫描速度、目录图稳定与 Agent 目录清单

日期：2026-10-30（同日按评审意见收窄：清单只含 D、E 盘，不再分「可以删」和「不可以删」）

这份说明只覆盖这一轮优化。安全模型仍以 `docs/superpowers/specs/2026-10-09-storage-audit-design.md` 为准：系统文件不删，执行前重新检查，本轮不新增删除能力。

## 为什么做

- 清理页打开或重新扫描时，每个缓存文件都走一遍删除判断，缓存文件很多时要等很久。
- 盘查整盘时，系统目录和 `node_modules` 这类目录里的每个文件都建记录，并向页面推送路径。
- 盘查期间目录占用图一直闪。进度条停在页面上方，扫描大约每 400 个文件就同步改一次页面。
- 项目页按可再生体积排名，读者看不出这是「哪里的可重建目录最占空间」。
- 导出的 `REPORT.md` 和 `inventory.json` 把每个项目和每条发现写两遍，Agent 要在里面找哪些目录值得处理。

## 目标

- 清理页先给出可直接清理的缓存体积，再统计只建议、不删除的系统目录。
- 盘查仍给出正确的目录总体积，但系统目录和可重建目录内部不再产生大文件、分类和子项目。
- 盘查期间目录图保持不动，进度文字最多每 0.5 秒更新一次。
- 项目页说明排名的含义，并列出每个可重建目录的完整路径。
- 导出一份短清单，只含 D、E 盘上项目里的可重建目录。Agent 一眼看到最大的几处在哪、多大、怎么恢复。

## 非目标

- 不改变删除、回收站和进程结束的规则。
- 不在导出文件里放删除脚本或文件内容。
- 导出不再判断「可以删」还是「不可以删」。Agent 会自己复核，清单只给事实。
- 不把浏览器缓存、安装包、视频、系统目录放进给 Agent 的清单。
- 不要求删完以后项目立刻还能运行。可重建目录删掉后，到恢复命令完成之前，项目无法运行或构建。
- 清理页的缓存测量不受 D、E 范围影响。那些缓存在用户目录里，和导出是两件事。

## 导出范围：只含 D、E 盘

导出只包含路径落在 D 盘或 E 盘的项目，子项目一并算。常量 `EXPORT_DRIVES = ("D", "E")`。盘查页默认勾选 D、E 里实际存在的盘；两个都不存在时默认勾选 C。

导出不再需要「是不是系统文件」的判断，原因是清单里每一条都是项目里的可重建目录，不是任意文件。D、E 盘根目录下的 `$RECYCLE.BIN`、`System Volume Information` 本来就由扫描器当作系统保留目录只累加体积，不进入，不需要新增逻辑。

D、E 盘都没有盘查结果时，导出返回「请先盘查 D 盘或 E 盘」。

## 已确认的行为

可重建目录沿用现有名字：`node_modules`、`.venv`、`venv`、`target`、`dist`、`build`、`.next`、`__pycache__`、`.gradle`；.NET 项目另加 `bin`、`obj`。

每个这样的目录单独记录：

- `path`：该目录自己的完整路径
- `kind`：上面的目录名
- `bytes`：该目录的体积

同一个项目里的多个 `node_modules` 都保留路径。现有的按名字合计仍然留给项目页的占比条。

给 Agent 的清单是一张表，按体积从大到小。只有体积不小于 `100 * 1024 * 1024` 字节的目录才展开，最多展开 30 条。更小的和超出 30 条的合并进 `rolled_up`：`{"count": int, "bytes": int}`。没有被合并的目录时两个值都是 0。

这两个数是编写者的判断，没有用你机器上的盘查数据核对过。常量名 `MIN_ENTRY_BYTES` 和 `MAX_ENTRIES`，之后看到真实清单再调。

每条记录的字段：`path`、`bytes`、`kind`、`project_path`、`dirty`、`tracked`、`restore`。清单不替 Agent 下结论，只带这些事实：

- `dirty` 取自项目的 `git.dirty`：`true` 有未提交改动，`false` 干净，`null` 没能确认。子项目自己没有 `.git`（`git.dirty` 为 `null`）时，沿用最近一层父项目的值。
- `tracked`：对每条已展开的目录运行 `git -C <项目根> ls-files -- <相对路径>`。输出非空为 `true`（目录里有被 git 跟踪的文件，不是纯构建产物）；输出为空为 `false`；git 不可用、不是仓库或超时（10 秒）为 `null`。`rolled_up` 里的小目录不检查。

恢复命令写在每一条上，工作目录是项目根：

| 条件 | 命令文案 |
| --- | --- |
| `node_modules`，根目录有 `pnpm-lock.yaml` | 在项目根目录执行 pnpm install |
| 否则有 `yarn.lock` | 在项目根目录执行 yarn install |
| 否则有 `package-lock.json` 或 `npm-shrinkwrap.json` | 在项目根目录执行 npm ci |
| 其他 `node_modules` | 在项目根目录执行 npm install |
| `.venv` 或 `venv` | 按项目说明重建虚拟环境 |
| `target` | 在项目根目录执行 cargo build |
| `dist`、`build`、`.next` | 按该项目的构建命令重新生成 |
| `__pycache__` | Python 会自动重新生成 |
| `.gradle` | 在项目根目录执行 gradle build |
| `bin` 或 `obj` | 在项目根目录执行 dotnet build |

同时存在多个锁文件时，按上表从上到下命中第一条。

`git status` 只跑有可重建目录的项目，仍最多 200 个，按项目体积从大到小。没有可重建目录的项目不跑 `git status`。

## 速度和界面

- 页面进度事件最多每 0.5 秒送出一次。完成和失败事件不丢。
- 进度条不再用位移动画。目录图的尺寸和数据没变时，不重建这张图。
- 清理扫描用目录枚举累加体积。测量时不调用 `is_safe_delete_target`、`deletion_allowed` 或 `Path.resolve`。跳过重解析点，以及名字是 `node_modules`、`.git`、`.pnpm-store`、`dockerdata` 的子目录。用户临时文件的天数用同一次枚举得到的修改时间。
- 可直接清理的目标全部测完后先通知界面，再测「只建议」和下载目录报告。下载报告仍只累计 50 MB 及以上的文件。
- 进入系统目录或可重建目录后只累加体积和文件数，不建文件记录，不产生子项目，也不保留更深层的目录图节点。系统目录本身仍作为一个色块，体积是整棵子树。
- 项目页默认排序的文案改为「按可重建目录占用」。页面说明：这是占空间排名，不是整项目可删排名。详情列出每个可重建目录的路径。旧盘查缓存没有路径列表时，仍显示原来的按名字合计。

## 导出文件

仍写 `exports/handoff-时间/REPORT.md` 和 `inventory.json`。`schema_version` 为 `2`。两份文件描述同一份清单。JSON 只含这些键：`schema_version`、`generated_at`、`drives`、`rules`、`items`、`rolled_up`。`drives` 只含 D、E 盘里实际存在的盘，每项只保留 `drive`、`total_gb`、`used_gb`、`free_gb`。

规则固定为这 3 条：

1. 只处理本清单列出的目录，不动项目源码，不动清单以外的任何路径。
2. 删除前确认路径仍然存在、目录名是清单里的种类。`dirty` 为 `true` 或 `null` 的项目先看 git 状态；`tracked` 为 `true` 说明目录里有被 git 跟踪的文件，不要删。
3. 删除后项目要先按 `restore` 恢复才能运行。本文件只有路径和元数据，没有文件内容。

报告是一张 Markdown 表：体积、路径、种类、未提交改动、已被 git 跟踪、恢复命令，加一行 `rolled_up` 的合计。没有可重建目录时，报告写「这次盘查没有识别到可重建目录。」
